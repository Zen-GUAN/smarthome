## 桥接模式：每设备两条自动化

HA 原生 mqtt 实体**当不了桥**——mqtt 实体的 command_topic 是 HA 对外发布的
出口，收到消息只会改实体自身状态，不会驱动 UIOT 设备。正确模式是每设备两条
自动化：

1. **入站(接收指令)**：`trigger: platform: mqtt, topic: <裸topic>` →
   模板判断 payload(`on`/`off`/空调`on#模式#温度`) → 调 UIOT 实体的服务
2. **出站(状态同步)**：`trigger: platform: state` → `mqtt.publish` 推
   `<topic>/up`

`/up` 后缀 topic 的语义：只更新巴法云端记录、不推送给订阅者——这是防止
状态回环的关键（如果推到裸 topic，HA 会再次收到自己发的状态当成指令）。

## 巴法 topic 类型后缀约定

| 后缀 | 类型 | 说明 |
|---|---|---|
| 001 | 插座 | |
| 002 | 灯 | 本项目所有灯用这个 |
| 003 | 风扇 | 净化器/新风候选 |
| 004 | 传感器 | |
| 005 | 空调 | 支持开关/模式/温度 |
| 006 | 开关 | |
| 009 | 窗帘 | |

- topic 名只允许字母数字（不允许下划线）
- 后缀类型错了米家侧识别不了（报"设备已被移除下线"类错误）
- 其他后缀不同步米家

## 空调指令格式

payload: `on` / `off` / `on#模式#温度`

模式代码：1自动 2制冷 3制热 4送风 5除湿 6睡眠 7节能，温度16-32，
尾部字段可省略。注意 UIOT 空调 hvac_modes 只有
[off, cool, heat, dry, fan_only] 无 auto——巴法模式 1/6/7 都映射到 cool。

## 合并组

一个 topic 控制多路灯（如"灯带"=磁吸灯+灯带两路）：入站自动化对实体
列表批量开关；出站自动化任一实体 on 即上报 on。特点是一开全开一关全关，
语音命名建议带位置词全名。

## 双注册问题

同一批物理设备在 HA 里可能有两份实体（如 UIOT 体系一份 + 涂鸦云一份）。
本项目桥接一律选 UIOT 正主（即时响应），涂鸦副本只做只读或备用：

- 温控器 climate（涂鸦）：延迟 30~90 秒，仅作空调备用通道
- 485x 空调（UIOT 的另一注册面）：与已桥空调同批，不重复桥接
- 判活方法：App 走本地通道、openapi 走云通道，是两条路，
  必须分别实测，不能只用"翻转后看跟随"判断（UIOT 状态延迟 15~30 秒）

## 凭据与连接

- HA ↔ 巴法：MQTT 9501(明文)/9503(TLS)，client_id 强制=巴法私钥，
  username/password 必须全空，详见 docs/02
- HA ↔ UIOT：openapi 网关 + AES 加密 + MD5 签名，见 scripts/uiot_control.py
- 脚本凭据统一走 .env，模板见 .env.example
